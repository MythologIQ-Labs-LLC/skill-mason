# Independently verified multi-method P0 composition (development only)

**Implementation:** [operator-multi-source-composition.mjs](../../src/backend/operator-multi-source-composition.mjs). **Objective:** compose a single portable Agent Skills candidate from **two to sixteen distinct original methods**, each with its **own** exact C4/C5 preflight and genuinely external source/operator approval path, without losing method-by-method refusal.

This is a backend-only companion to [one-method operator composition](operator-source-composition-v1.md), not a new public `create` switch or an assertion that real rights have been signed. No independent operator keys, legal acceptance, host permissions, or actual host test witnesses have been supplied. Never expose `selections` or its trust keys to user-controlled recipe input.

`composeOperatorBoundMultiP0({sourceRegistry,recipe,selections,expectedSnapshotSha256,holoPath,holoSha256,outputRoot,...})` requires **one** external independent snapshot SHA-256 plus **one** `selection` for **each** recipe method. Each selection includes `methodId`, `preflight`, `operatorTrust`, `expectedSourceBindingSha256`, `expectedMethodSha256`, `expectedPackageSha256`, `readOperatorAcceptance`, and `assertSignedMethod`.

- Before any signer or Prism call, verify every selected method's complete pinned original bytes, required-outcome coverage, host, source-preflight binding, historic snapshot commit, independently held source/method/package digest and exact one-to-one selection. A second method cannot borrow the first method's scope, evidence or approval.
- Reverify each operator's Ed25519 signature, expiry and revocations independently against the actual final composer assurance subject; request the unrelated signed four-fact evidence and invoke the same pinned P0 guest **once per method**. No speculative partial candidate can be written if any one method refuses.
- Preserve separate `sourceBindingSha256`, `sourceAcceptanceProofSha256` and `proofDigest` for every method in the existing strict receipt. Validate the population and then exclusively seal and reread the final complete package.
- Return one `MULTI_METHOD_STRICT_SIGNED_SOURCE_P0_DEVELOPMENT_CANDIDATE` with sorted per-method proof references and the **complete final package SHA-256**. Always `productionEligible:false`, `hostValidated:false`, `guestAssurance:'P0 unverified'`. Signed-four-fact signature replay and operator trust custody are the separately configured delegates' responsibility.

**Exact real source fixture:** [two original first-party methods](../../tests/operator_multi_source_composition.test.mjs): `ci-failure-triage-v5` plus `release-readiness-review-v2`. Their bytes are verified against historical original Git blob IDs and SHA-256 before composition, not copied from an unverified catalog. Tests use distinct **ephemeral fixture Ed25519 keys per method for both approval and fact assertions** (four test keys) and an explicitly mocked Prism runtime; no production-rights proof, genuine operator custody, native real guest execution or independently witnessed host task is claimed by these tests.

**Behavior checked:** combine two methods into a single sealed `SKILL.md` + `SOURCES.json` + `RECEIPT.json` + `skill-mason.json`; identical output when method approval input order changes; wrong/missing original pins, duplicate or omitted selection, changed route, host, method or snapshot refused *before signers*; second-method signed denial, missing approval and stale operator revocations produce **zero** package output; and existing complete artifacts cannot be overwritten.

**Remaining completion blockers:** This proves the **composition mechanism**, not that two source procedures are behaviorally compatible or jointly adequate for an arbitrary real user task. We still need independent source rights approval, a bound original C2 outcome map, trusted operator key custody, actual native Prism proof replay, and real agent-host outcome comparisons before any release qualification. Method count does not imply useful capability coverage.
